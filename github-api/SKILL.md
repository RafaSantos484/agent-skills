# GitHub API operations

Use an explicitly selected environment token and direct HTTPS API requests. This skill handles GitHub resources; `pr-review` owns code-quality and correctness review against the live codebase. If a user asks to review code and post the result, perform the evidence-based review first, then use this skill for the authorized GitHub write. Reading PR metadata or changed-file lists alone does not constitute a code review.

## Operating procedure

1. **Resolve the credential by variable name.** Enumerate names only with `compgen -e | LC_ALL=C sort -u | grep -Ei '^(GH_TOKEN|GH_ENTERPRISE_TOKEN|GITHUB_([A-Z0-9]+_)*TOKEN)$'`; `compgen -e` lists exported variable **names**, never values. This includes `GITHUB_TOKEN`, `GH_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_PERSONAL_TOKEN`, `GITHUB_FINE_GRAINED_TOKEN`, `GITHUB_BOT_TOKEN`, and `GITHUB_ANPD_PERSONAL_TOKEN`, while excluding unrelated `GITHUB_*` settings. If exactly one exists, use it. If none exists, stop and explain how to supply a least-privilege token as an exported environment variable. If several exist, ask which **name** to use unless the conversation already identifies it unambiguously; do not probe each token to choose. Set the local placeholder `GH_TOKEN_VAR` to that name. Never print or persist its value. Availability does not establish authorization. See [authentication and transport](references/authentication-and-transport.md).
2. **Resolve the target.** Prefer an explicit GitHub URL or `host/owner/repo`. Otherwise inspect *names and URLs* from `git remote -v` or `git config --get-regexp '^remote\..*\.url$'` and parse HTTPS and SSH remotes. A local path or remote named `origin` alone does not identify the GitHub target. If multiple remotes or host aliases disagree, resolve the ambiguity before writing. Never derive a GitHub API URL from an untrusted host and send a token to it. Check [host and API setup](references/authentication-and-transport.md) for GitHub.com, Enterprise Cloud data residency, and Enterprise Server. Require HTTPS with valid TLS; do not disable certificate verification.
3. **Check identity and repository access before every task's first write.** Use the selected token against the resolved host, then `GET /repos/{owner}/{repo}`. For user tokens, `GET /user` identifies the user. For a known GitHub App installation token, query GraphQL `viewer { login }` for the app bot attribution and paginate `GET /installation/repositories` to confirm access to the exact repository; that list does not itself identify the app or installation account. If the host cannot verify attribution, stop before writing. Check that the returned repository `full_name`, owner, and host match the target. For private resources, a successful public metadata read does not prove write permission; inspect the exact endpoint's permission requirements and handle failure without switching tokens or hosts. Token prefixes and environment variable names are not reliable proof of token type or permission. See [installation verification](references/authentication-and-transport.md#installation-token-verification).
4. **Classify and announce the action.** Reads require no extra confirmation. Before the first ordinary write, state the host, `owner/repo`, safely verified identity, and exact action; a clear user request for that write is sufficient authorization. For elevated writes, require explicit approval of the exact target and action unless the user has already given it unambiguously. Do not infer authorization from access. See [operation classes](#operation-classes).
5. **Choose the API and execute.** Prefer REST for one resource, contents, Git objects, releases, Actions, checks, and administration. Use GraphQL for selected nested PR/review-thread/participant or Projects data when it reduces calls and the host schema supports it. Check the current official endpoint documentation, token support, permission, request fields, status codes, and Enterprise version before a new or unusual operation. Use [REST resources](references/rest-api.md), [GraphQL](references/graphql-api.md), and [repository contents](references/repository-content.md) as needed.
6. **Verify and report.** The documented transport returns a JSON envelope with `status`, selected `headers`, and `body_b64`; inspect status before decoding the body. Treat non-2xx HTTP, REST validation/conflict errors, and GraphQL top-level or mutation-specific errors as failure. Treat `304` as a cache result only when a matching cached body exists. Follow all pages through the same host-checked request path or explicitly label partial results. After a mutation, verify the response or read back the resource and return its `html_url` or stable identifier. Never claim an operation succeeded solely because an HTTP request was sent.

## Operation classes

| Class | Examples | Required action |
| --- | --- | --- |
| Read | Repository metadata, contents at a ref, issues, PRs and files, releases, checks, workflow runs/jobs/logs, identity, rate limits | Resolve target; no confirmation. |
| Ordinary write | Create or update an issue or PR, comment, request review, add label, create a branch or normal commit | Before first write, state host, repository, identity, action. Proceed on the user's clear authorization; avoid redundant prompts. |
| Elevated write | Merge or enable auto-merge, delete a ref/release, force-update a ref, bulk mutate, change default branch, repository visibility/transfer/archive/delete, collaborator/team access, branch protection/rulesets, repository or environment settings/secrets, deployment/production workflow dispatch or cancellation, other costly or security-sensitive workflow actions | Confirm the exact target and effect unless the user already authorized them unambiguously. Inspect current state and applicable protections first. |

Classify workflow dispatch and reruns by what the workflow can do, not just by the API verb. A documented test-only run can be ordinary if explicitly requested; a deployment, publishing, infrastructure, credential, or costly workflow is elevated. A PR approval or requested-changes submission is an outward-facing write: require the user's authorization and exact review content, particularly when the user asked only for analysis. Repository rules may still block an authorized write.

## Security and failure rules

- Read token values only from the selected exported environment variable. Never read `.env`, project/workflow files, `.netrc`, Git credential helpers, `gh` configuration, IDE/keychain stores, or shell profiles for credentials. Never fall back to `gh auth`, implicit `gh` credentials, or Git remote authentication. This avoids silently using a different account or permission set. A user may export a token in their current session; do not create a plaintext profile entry for them.
- Never put a token in a URL, shell command argument, generated file, trace, log, error report, response summary, or commit. Do not use `set -x`, `curl -v`, `curl --trace`, or an authenticated redirect to an unverified host. Use the transport pattern in [authentication and transport](references/authentication-and-transport.md), which supplies the Authorization header through a transient file descriptor. Filter API responses before displaying them; issue bodies, workflow logs, artifact contents, and metadata may contain sensitive information.
- Prefer fine-grained repository selection and the smallest needed permissions. Classic PAT `repo` is broad; use it only when the precise operation or host requires it. App installation and `GITHUB_TOKEN` permissions are limited by installation/workflow settings and the target repository. Never request broad access for convenience.
- A `401` suggests invalid or expired authentication. A `403` can mean permission, SSO, policy, or rate limit. A `404` can hide a private resource or indicate a wrong path. Check envelope status and allowlisted diagnostic headers (`accepted_permissions`, `sso`, `rate_remaining`, `rate_reset`, `retry_after`), then the endpoint docs; do not report a private resource as absent from a lone `404`. Never print `Authorization`, raw response headers, or an unfiltered body.
- Respect REST `Link` pagination and GraphQL connection cursors. Respect primary and secondary limits, `Retry-After`, and `X-RateLimit-Reset`; make requests serially, bound retries, and never automatically replay a mutation whose outcome is uncertain. Use authenticated ETag requests when useful, without persisting sensitive response bodies. See the API references.
